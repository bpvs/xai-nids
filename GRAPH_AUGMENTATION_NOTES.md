## NOTE 1 — Test-set-only, self-consistent scaling

`graph_transform.py` preprocesses the **TEST set on its own statistics** (MinMax
fit on test), rather than reusing the train-fitted scaler from
`data_utils.load_data()`. This is deliberate: the graph stage needs the sample
scaled self-consistently while preserving row identity (so each node traces back
to its original test index).

**Consequence:** the entire before/after comparison is a
**test-set vs. test-set-graph** comparison. The test set's attack fraction
(~0.569) differs from the train+test combined figure (~0.481) because NSL-KDD's
test set was intentionally constructed with a harder, shifted distribution
(it contains attack types absent from training). This is internally consistent —
the shift the comparison measures is attributable to the graph step, not to a
train/test scaling mismatch.

Where it lives in code: `graph_transform.py::load_and_preprocess_test()` and the
header docstring; `profile_after.py` NOTE 1.

## NOTE 2 — Before/after comparison is scaled-vs-scaled, not raw-vs-scaled

`profile_before.html` (the human-readable reference) profiles the **raw-valued**
data. But `after.parquet` holds **MinMax-scaled** features. Comparing raw
magnitudes against scaled ones would show a "shift" that is purely a scaling
artifact, not an effect of the graph transformation.

So the `.compare()` report in `profile_after.py` rebuilds a **scaled** version of
the before-features (identical preprocessing to the graph stage) and compares
**scaled-before vs. scaled-after** on the shared original columns. Any
distribution shift in that report is therefore genuinely attributable to the
graph step (specifically: to sampling 10K rows and to the graph-feature
addition), not to scaling.

The raw `profile_before.html` is kept as the human-readable reference; it is not
the artifact used for the fair comparison.

Where it lives in code: `profile_after.py::build_scaled_before()` and NOTE 2 in
its header docstring.

## Pipeline artifacts produced so far (graph-augmentation extension)

- `reports/profile_before.html`     — raw test data profile (human reference)
- `data/processed/after.parquet`    — 10K graph-augmented table
                                       (41 feats + graph_degree + graph_pagerank
                                        + label_binary + is_explained + orig_test_idx)
- `data/processed/sample_manifest.json` — seed, sampled indices, and the shared
                                       "explained" record positions (reproducibility;
                                       downstream stages read this instead of
                                       re-rolling np.random.choice)
- `reports/profile_after.html`      — standalone augmented-table profile
- `reports/profile_comparison.html` — **the before/after graphDB deliverable**
- `reports/profile_graph_feats.html`— dedicated profile of the two new graph feats

Graph build parameters: test-only population, 10K stratified sample (seed=42),
kNN k=10, bidirectional edges (for well-defined PageRank), FalkorDB via Docker.

## NOTE 3 — ydata-profiling package rename (migration watch-item)

`ydata-profiling` now emits a DeprecationWarning: it is being succeeded by
**`fg-data-profiling`**, with the import changing from `import ydata_profiling`
to `import data_profiling`. (The older EDA work on this project already referenced
fg-data-profiling, so this is a known lineage.)

Action: do NOT migrate mid-experiment — consistency across the before/after runs
matters more than the package name. When convenient, swap the import in all three
profiling stages (`profile_before.py`, `profile_after.py`) in one pass:
    from ydata_profiling import ProfileReport   ->   from data_profiling import ProfileReport
and update requirements/env accordingly. Re-run all profiles together after the swap
so before/after stay generated by the same version.

Also harmless (ignore): a `SettingWithCopyWarning` is raised from *inside*
ydata-profiling's own `utils/dataframe.py` during report generation. It is the
library's internal pandas usage, not our code, and requires no action.
